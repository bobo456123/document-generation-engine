## 3. 已验证能力

- Umi/React 请求能够与 Spring Controller 端点关联。
- 每条关联保留前后端文件、Commit、符号和行号证据。
- HTTP Method 不一致不会误关联。
- 一个请求匹配多个后端端点时输出冲突，不静默选择。
- 大型 Java 文件无法由当前 Tree-sitter 组合处理时降级并计量，不标记为完整 verified。
- 真实候选能够生成不可变 DocumentationModel 和 Markdown 修订。
- 新文档包含阻塞审核项，不能直接发布。
- “线索转化”已聚合四个写接口并形成首份金标草案，明确记录状态条件、必选客户、可选项目和失败分支。
- 已准备 5 个覆盖状态变化、提交审批、权限维护和批量修改的候选修订，等待用户确认最终试点集合。
- 每个新生成修订记录来源快照和前后端 Commit，可追溯到确定的分析基线。
- 已通过 Anthropic Messages 兼容接口和 `glm-5.3` 完成一次真实结构化生成：线索转换修订 7，状态为 `needs_review`。
- AI 输入仅包含筛选后的相对文件路径、符号、行号和限长摘录，不包含仓库绝对路径；所有 AI 修订自动增加阻塞人工复核项。

## 4. AI 试点评测

| 检查项 | 修订 7 结果 |
|---|---|
| 事实准确性 | 已覆盖 `lookupLead` 失败不阻塞、项目失败留在第二步、状态回写、转换记录成功码校验 |
| 步骤覆盖 | 覆盖客户、项目、状态回写、转换记录和成功关闭；遗漏允许状态、客户 ID 缺失中止和项目跳过分支 |
| 无证据陈述 | 出现“项目关联必然存在”等表述风险，尚未经 CRM 研发确认 |
| 审核门禁 | 自动加入 blocking review item，数据库状态为 `needs_review` |
| 稳定性 | 扩充条件/常量证据后的 3 次调用均未生成合法对象，其中 2 次 Schema 不匹配、1 次无模型响应；失败均未落库 |

修订 7 相比只输入 `BusinessFeature` 的修订 6 明显改善，但尚不足以批量生成其余四个候选。当前模型兼容服务对较长的结构化输入不稳定，需要继续压缩 Prompt、拆分生成阶段，或由供应商修复 Anthropic Messages 结构化输出兼容性。

## 5. 当前质量缺口

- 部分候选标题仍来自组件名或 Java 方法名，不是可直接发布的业务名称；线索转化已验证可通过页面调用上下文改善聚合粒度。
- 静态事实尚未完整连接页面操作顺序，模板步骤必须人工确认。
- 41 个大型或复杂 Java 文件需要评估 Tree-sitter 升级、分段策略或 JavaParser Sidecar。
- 已完成单个真实 AI 样例评测，但未达到 3 至 5 个样例，人工修改时间仍未测量。
- 尚未提供人工页面截图。
- 线索转化修订 8 已首次真实发布到飞书测试知识库：复用部分失败留下的节点，写入 22 个 Block，本地审计为 completed。

## 6. 阶段结论

当前结论为 `CONDITIONAL_GO`：代码事实提取、跨栈关联、中间模型、Markdown、审核门槛和飞书适配器的本地技术路线成立。要将 MVP 判定为 `GO`，仍需完成：

1. 解决当前模型兼容接口的结构化输出稳定性，并完成其余 4 个候选的金标评测。
2. 由熟悉 CRM 的人员确认业务功能名称、入口、步骤和结果。
3. 为试点文档提供至少一张真实截图。
4. 确认首次真实写入；如不希望发布到空间根目录，提供可选父节点。
5. 对重复发布、图片位置和飞书排版进行人工验收。
