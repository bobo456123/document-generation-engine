# Goal 5：完成真实项目端到端验收

> 对应技术方案：MVP 用户流程、调研 Spike、测试策略、风险验证和 MVP 完成定义  
> 前置条件：[Goal 4：完成飞书发布闭环](./GOAL-04-FEISHU-PUBLISHING.md) 已通过确认  
> 本 Goal 是 MVP 技术路线的最终验收，不是继续扩展功能范围

## Goal

在一个用户明确授权的真实 Spring Boot + Vue/React 项目中，选择 3 至 5 个代表性业务功能进行端到端试点，证明系统能够以可追溯证据还原业务功能、生成可用的图文操作文档，并把审核结果幂等发布到飞书测试知识空间，同时量化准确性、人工成本和技术缺口。

## 结果

- 明确记录试点项目、前后端路径、技术栈、分析范围、Git Commit（若存在）和非生产/生产等价状态。
- 由用户确认 3 至 5 个代表性功能，至少覆盖：
  - 一个创建或提交类操作；
  - 一个编辑或状态变化类操作；
  - 一个带权限、条件显示或前后端冲突的操作。
- 对每个功能跑通：

```text
本地源码 → 扫描 → 前后端分析 → Feature Linker
→ BusinessModelSnapshot → DocumentationModel
→ Markdown → 人工截图 → 本地预览 → 审核
→ 飞书测试知识空间创建或更新
```

- 每个关键业务结论都能定位到代码、配置、注释或人工输入；无法证明的内容明确标记为推断、冲突或未知。
- 为每个功能保存业务模型快照、文档修订、截图资源、审核记录和飞书发布映射。
- 由至少一名熟悉代码的研发人员审查证据和调用路径。
- 在条件允许时，由至少一名目标业务读者审查操作文档的可读性和可操作性；若无法获得业务评审，必须明确记录该验证缺失。
- 对试点采集并汇总以下指标：
  - 关键路径关联覆盖率；
  - `verified`、`inferred`、`conflicted`、`unlinked` 数量；
  - 事实准确率和步骤覆盖率；
  - 无证据陈述数；
  - 每篇文档人工修改项数和修改耗时；
  - 首次生成耗时、重复运行耗时；
  - 飞书首次发布与重复发布成功率；
  - 解析失败文件数和人工映射数量。
- 形成一份试点验收报告，给出明确结论：
  - `GO`：MVP 技术路线成立，可以进入产品化；
  - `CONDITIONAL_GO`：核心闭环成立，但必须先解决列出的限制；
  - `NO_GO`：关键假设不成立，并说明证据和替代方向。
- 将真实项目暴露出的通用问题转化为后续任务，不在本 Goal 中无边界扩展实现。

## 约束条件

- 只分析用户明确授权的项目目录和 Git Commit，不扫描无关仓库或用户目录。
- 分析保持静态、只读，不执行目标项目、不连接生产数据库、不调用生产业务接口。
- 不上传完整企业源码；发送给模型的内容必须符合已确认的模型供应商、数据保留和跨境合规要求。
- 若合规要求尚未确认，不得发送企业源码或摘录到外部模型；可以使用脱敏 Fixture 验证其余流程并将真实模型阶段标记为阻塞。
- 飞书发布只使用明确授权的测试知识空间；发布前必须显示目标位置和文档清单。
- 所有 AI 生成的新修订都必须经过人工审核，不能因为是最终验收而跳过。
- 不为了提高指标而隐藏未关联项、删除冲突或把人工映射标记为代码事实。
- 指标分母、计算方法和人工判定标准必须在评测前固定，不能在看到结果后调整。
- 真实项目中的客户数据、连接字符串、Token、Secret 和个人信息不得进入日志、数据库、报告或模型 Prompt。
- 不在本 Goal 增加自动截图、Git Diff、RAG、多 Agent、Web 帮助中心、多租户或生产发布。
- 如果试点暴露架构级问题，应暂停、记录证据并提出变更建议，不通过大量特例掩盖问题。
- 不自动提交、推送或修改被分析项目。

## 确认

- 3 至 5 个试点功能均有独立的分析运行、业务模型快照、文档修订和审核记录。
- 每个功能至少有一条从页面入口到 Controller、Service 和主要业务对象的可审查路径；无法达到时必须计入失败或部分成功，而不是删除该样例。
- 抽样检查所有 `verified` 结论，证据文件、Commit、符号和行号真实存在。
- 研发评审记录明确标注正确、错误、遗漏和冲突，不只给出主观总分。
- 业务评审能够按文档完成操作步骤，或明确列出阻止完成的文档问题。
- 每篇文档至少关联一张真实人工截图，Markdown 预览和飞书中的图片位置一致。
- 所有发布文档均为已审核修订；飞书目录、文档标题和层级符合预期。
- 对同一文档执行重复发布，没有生成不可识别的重复节点或重复文档。
- 端到端 CLI 流程在干净环境中至少完整重复执行一次，并记录命令、耗时和结果。
- 系统失败不会覆盖已审核修订，不会把失败发布记录成成功，也不会泄漏凭证或敏感源码。
- 根目录 `build`、`lint`、`typecheck`、`test` 全部通过，飞书集成测试通过。
- 验收报告包含原始测量数据、指标算法、失败案例、人工映射、已知限制、风险和 GO/CONDITIONAL_GO/NO_GO 结论。
- MVP 只有在真实项目上可重复完成全链路，并满足技术方案完成定义时才标记完成。

## 完成边界

本 Goal 只验证技术路线和 MVP 价值。发现的 V0.2 及以后能力进入后续路线图，不在验收过程中顺手实现。
